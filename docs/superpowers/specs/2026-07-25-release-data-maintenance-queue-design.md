# 版本发布与数据维护叫号系统设计规格

- 日期：2026-07-25
- 状态：已完成交互式设计确认，等待书面规格复核
- 部署目标：单机 Docker Compose，可在后续扩展为独立数据库或多实例部署
- 业务时区：Asia/Shanghai

## 1. 目标

建设一个面向开发人员、运维管理员和运维组长的内部叫号系统。开发人员提交版本发布或数据维护任务后，系统依据操作日期的值班表、操作时间、当天任务数量、人员可用性和当月已完成实际耗时自动选择运维负责人。

系统必须做到：

1. 自动分配结果确定、并发安全且可解释。
2. 当天值班人员能看到当天所有任务的整体情况。
3. 当前负责人可叫号、执行、完成和直接转交任务。
4. 运维组长可维护账号和值班表、调整负责人、标记人员不可参与并批量重新分配。
5. 所有关键操作留存不可覆盖的审计记录。
6. 首版预留钉钉通知接口，但不实际连接钉钉。

## 2. 首版范围

### 2.1 包含

- 本地账号密码认证。
- 开发人员、运维管理员、运维组长三类可组合角色。
- 版本发布和数据维护取号。
- Excel 值班表校验、预览和导入。
- 自动分配、人工转交、组长调整和批量重新分配。
- 待执行、执行中、已完成三态任务流程。
- 全量任务中心、角色工作台、统计和审计日志。
- Docker Compose 容器化部署、MySQL 持久化、健康检查和备份恢复脚本。
- 叫号通知事件与异步通知扩展接口。

### 2.2 不包含

- 首版不对接 LDAP、OIDC 或企业统一身份认证。
- 首版不调用钉钉接口，不发送真实钉钉消息。
- 首版不实现多组织、多租户或跨时区。
- 首版不提供业务数据物理删除。
- 首版不建设独立系统名称字典，系统名称使用自由输入和历史联想。

## 3. 技术架构

采用 Spring Boot 3 + Vue 3 + TypeScript + MySQL 8：

- `web` 容器：Nginx 托管 Vue 构建产物，并将 `/api` 反向代理到后端。
- `api` 容器：Spring Boot 3，负责认证授权、任务、调度、值班导入、统计、审计和通知事件。
- `db` 容器：MySQL 8，使用命名持久化卷保存数据。
- Flyway 管理数据库版本。
- Docker Compose 统一拉起三个容器，并通过健康检查控制启动顺序。

模块边界：

- `identity`：用户、角色、登录、密码和账号状态。
- `task`：取号、任务查询、状态流转、叫号与完成。
- `scheduling`：自动分配、候选池、排序、日期级调度锁。
- `roster`：值班表模板、校验预览、确认导入和导入批次。
- `assignment`：转交、手工调整、重新分配和分配历史。
- `reporting`：当天任务数、月度实际耗时和分类统计。
- `audit`：关键业务和管理操作的审计日志。
- `notification`：通知事件、发送适配器、失败重试；首版只记录事件。

前端不得直接指定自动分配结果。自动分配、转交和重新分配均由后端校验并在事务中提交。

## 4. 角色与权限

### 4.1 开发人员

- 登录并修改自己的密码。
- 新建取号。
- 查看本人创建任务的详情、负责人和实时状态。
- 不能查看其他开发人员的任务。
- 不能修改负责人或推进运维执行状态。

### 4.2 运维管理员

- 查看任务中心的全部任务。
- 工作台默认展示操作日期为当天的全部任务，并突出待执行、执行中和需要人工处理任务。
- 对自己当前负责的待执行任务点击“叫号”。
- 对自己当前负责的执行中任务填写实际耗时并完成。
- 直接转交自己当前负责的未完成任务。
- 不能操作由其他管理员负责的任务。

### 4.3 运维组长

- 拥有全部任务和管理数据的查看权限。
- 创建、停用账号，重置初始密码，分配角色。
- 导入和维护值班表。
- 标记人员在指定日期不可参与。
- 手工调整任意未完成任务的负责人。
- 发起人员当天待执行任务的批量重新分配。
- 查看统计和审计日志。

角色可组合。仅有运维组长角色的账号不进入自动分配候选池；同时拥有运维管理员角色时进入候选池。

## 5. 取号字段和校验

开发人员提交以下字段：

| 字段 | 规则 |
|---|---|
| 类别 | 必填，只能是“版本发布”或“数据维护” |
| 系统名称 | 必填，自由输入，去除首尾空格 |
| 预计耗时 | 必填，正整数分钟 |
| 操作流程编号 | 两类任务均必填 |
| 操作开始时间 | 必填 |
| 操作结束时间 | 必填，必须晚于开始时间，可跨自然日 |

操作开始日期记为 `D`。值班匹配、当天任务数量和人员不可参与判断均基于 `D`。业务判断使用 Asia/Shanghai，持久化时间戳统一存储为 UTC。

叫号编号格式为 `OPS-YYYYMMDD-0001`，其中日期是取号日期，序号每日从 1 开始并在并发场景下保持唯一。

## 6. 值班表

Excel 模板固定三列：

1. `值班日期`
2. `二线管理员账号`
3. `三线管理员账号`

导入校验：

- 日期有效且同一批次不重复。
- 二线和三线账号存在、已启用并具有运维管理员角色。
- 同一天二线和三线不能是同一账号。
- 整个文件校验通过后才允许确认导入。
- 确认导入以单个事务覆盖文件中对应日期的原值班数据。
- 保存导入人、原文件名、文件摘要、行数、覆盖日期和校验结果。

新建任务必须存在 `D` 日值班表。进入公平分配时还必须存在 `D+1` 日值班表，以便可靠排除次日二线和三线；缺失时拒绝本次取号并提示需要补充的日期。

## 7. 自动分配规则

### 7.1 通用约束

- 停用账号和在 `D` 日被标记为不可参与的人员是硬排除对象。
- 自动分配在日期 `D` 的数据库调度锁内顺序执行。
- 每次分配保存命中规则、候选人及其排序指标快照。
- 新建任务没有任何可用候选人时拒绝取号且不创建任务；批量重新分配没有候选人时按第 9.3 节保留原负责人。

### 7.2 规则优先级

按以下顺序匹配，命中后停止：

1. **21:00 后取当天操作号**
   - 条件：取号时间不早于 21:00，且 `D` 是取号当天。
   - 优先分给 `D` 日二线，不受 3 个任务阈值影响。
   - 二线不可参与时分给 `D` 日三线。
   - 二线和三线均不可参与时进入公平分配。

2. **白天操作**
   - 条件：操作开始时间在 08:30（含）至 17:30（不含）。
   - 始终优先分给 `D` 日二线，不受 3 个任务阈值影响。
   - 二线不可参与时分给 `D` 日三线。
   - 二线和三线均不可参与时进入公平分配。

3. **非工作时间操作**
   - 条件：操作开始时间早于 08:30，或不早于 17:30。
   - `D` 日二线当前任务数少于 3 时分给二线。
   - 否则，`D` 日三线当前任务数少于 3 时分给三线。
   - 否则进入公平分配。
   - 二线不可参与时直接判断三线；三线也不可参与或已达到 3 个时进入公平分配。

17:30 整按非工作时间处理。

### 7.3 公平分配

候选池：

- 所有已启用且拥有运维管理员角色的账号。
- 包含 `D` 日已经达到 3 个任务的二线和三线。
- 排除 `D` 日不可参与人员。
- 排除 `D+1` 日二线和三线值班管理员。

候选人按以下字段依次升序排列：

1. `D` 日当前负责的任务数量。
2. `D` 所在月份已完成任务的实际耗时合计。
3. 最近一次被分配时间，空值最优先。
4. 用户 ID，保证结果稳定且可复现。

“`D` 日当前负责的任务数量”统计操作开始日期为 `D`、当前负责人为该管理员的全部任务，已完成任务仍计数；任务转交后由新负责人计数。

“月度实际耗时”只统计已完成任务，按任务操作开始日期归入月份，并全部计入完成任务时的最终负责人。未完成任务不计月度实际耗时。

“最近一次被分配时间”取该管理员最近一次成为新负责人的时间，包含自动分配、直接转交和组长调整。

## 8. 任务生命周期

状态只有：

1. `PENDING`：待执行，取号并完成分配后的初始状态。
2. `IN_PROGRESS`：执行中，当前负责人点击“叫号”后进入。
3. `COMPLETED`：已完成，当前负责人填写实际耗时并完成后进入。

叫号：

- 只有当前负责人能对待执行任务看到和点击“叫号”按钮。
- 叫号记录操作者和叫号时间。
- 叫号成功后生成 `TASK_CALLED` 通知事件。
- 开发人员在本人任务详情中立即看到执行中状态。

完成：

- 只有当前负责人能完成执行中任务。
- 必须填写大于 0 的实际耗时分钟数。
- 保存完成时间，并将实际耗时计入最终负责人。
- 已完成任务不能再次叫号、转交或调整负责人。

所有状态更新使用数据库并发版本号；过期页面提交返回冲突，由用户刷新后重试。

## 9. 转交、调整和重新分配

### 9.1 当前负责人转交

- 当前负责人可以直接转交自己的待执行或执行中任务，无需目标人员确认。
- 必须选择新负责人并填写原因。
- 目标必须是启用的运维管理员，且未被标记为 `D` 日不可参与。
- `D+1` 日值班排除只约束自动公平分配。人工转交给次日值班人员时展示提示，但不禁止。

### 9.2 组长手工调整

- 组长可以调整任意待执行或执行中任务。
- 目标约束与直接转交相同。
- 原负责人、新负责人、操作者、原因和操作时间写入分配历史与审计日志。

### 9.3 不可参与与批量重新分配

- 组长为人员添加 `D` 日不可参与记录，必须填写原因。
- 系统先预览该人员操作日期为 `D` 的全部待执行任务。
- 组长确认后，任务按确定顺序逐项重新运行自动分配。
- 执行中任务不自动移动，组长在任务详情中单独调整。
- 某项任务没有可用候选人时保留原负责人，标记“需要人工处理”，继续处理其他任务并返回逐项结果。

## 10. 页面

前端采用角色导航，首页主体采用任务队列。

| 页面 | 内容 |
|---|---|
| 登录 | 本地账号密码登录、首次登录强制修改初始密码 |
| 工作台 | 今日值班、当天全量队列、我的任务、状态计数、人工处理提醒 |
| 我要取号 | 取号表单、字段校验、自动分配结果 |
| 任务中心 | 全部任务；按日期、类别、系统、状态、创建人和负责人筛选 |
| 任务详情 | 基本信息、分配原因、叫号、完成、转交、状态与分配时间线 |
| 值班管理 | 下载模板、上传校验、预览、确认导入、导入历史 |
| 人员与可用性 | 账号、角色、启停、不可参与和批量重新分配 |
| 统计 | 当日任务数、月度实际耗时、类别和系统维度统计 |
| 审计日志 | 登录、任务、分配、导入和账号管理操作 |
| 个人中心 | 修改自己的密码 |

## 11. 数据模型

- `users`：账号、显示名、BCrypt 密码哈希、首次改密标记、启停状态、最后登录时间。
- `roles`、`user_roles`：角色定义和账号角色关系。
- `duty_rosters`：值班日期、二线用户、三线用户，日期唯一。
- `tasks`：编号、类别、系统名称、预计分钟数、流程编号、操作时间范围、创建人、当前负责人、状态、叫号时间、实际分钟数、完成时间、命中规则、人工处理标记和并发版本号。
- `assignment_histories`：分配类型、原负责人、新负责人、原因、候选排序快照、操作者和时间。
- `unavailability`：人员、日期、原因和创建人；人员与日期唯一。
- `roster_import_batches`：文件元数据、摘要、校验和导入结果。
- `audit_logs`：操作者、动作、对象类型、对象 ID、变更前后摘要、来源 IP 和时间。
- `notification_events`：事件类型、接收对象、载荷、状态、重试次数和失败原因。
- `schedule_date_locks`：调度日期唯一行，用于 `SELECT ... FOR UPDATE` 串行化同日分配。
- `daily_ticket_sequences`：取号日期和最后序号，用于并发安全生成叫号编号。

## 12. 通知扩展

首版在叫号事务成功后写入 `TASK_CALLED` 通知事件，但只在站内展示任务状态，不调用外部接口。

后续钉钉适配器读取事件并向任务创建人发送通知。届时用户资料增加钉钉用户标识，部署环境增加钉钉应用凭证。

通知发送必须在任务事务提交后异步执行。发送失败不回滚叫号，记录失败原因并按退避策略重试；超过次数后在组长工作台提示。

## 13. 异常处理

- 缺少 `D` 日值班表时禁止取号。
- 公平分配需要但缺少 `D+1` 日值班表时禁止取号并提示缺失日期。
- Excel 任意一行校验失败时整批不写入。
- 非法状态、越权操作和并发版本冲突返回明确的业务错误。
- 调度锁短暂冲突自动有限重试，超过次数后提示用户重新提交。
- 重新分配无候选人时保留原负责人并标记人工处理。
- 通知发送失败独立重试，不阻塞核心业务。

## 14. 安全和审计

- 密码使用 BCrypt 哈希，系统不保存或展示明文密码。
- 初始密码首次登录必须修改。
- 组长重置密码后，该账号下次登录同样必须修改新初始密码。
- Spring Security 在后端同时校验角色和任务归属。
- 登录失败按账号和来源 IP 限流。
- 停用账号每次请求都会被拒绝，不依赖旧令牌中的状态。
- 访问令牌由部署环境中的密钥签名，并通过 HttpOnly、SameSite Cookie 传递。
- 初始化时通过环境变量创建首名运维组长；随后由组长维护其他账号。
- 关键业务与管理操作记录来源 IP、操作者和变更摘要。
- 业务数据不提供物理删除接口。

### 15.1 调度单元测试

- 执行备份并在新数据卷验证恢复结果。

## 16. 部署与运维

`.env` 至少配置：

- MySQL 数据库名、账号和强密码。
- 访问令牌签名密钥。
- 首名组长账号、显示名和初始密码。
- Spring profile 和 Asia/Shanghai 业务时区。
- 未来钉钉应用参数；首版保持为空。

MySQL 使用命名卷。项目提供显式备份和恢复脚本，恢复操作必须指定目标卷或数据库，不自动覆盖未知目标。应用日志统一输出到标准输出，容器日志由部署环境轮转。

## 17. 验收标准

1. 使用一条 Docker Compose 命令可以启动系统和 MySQL。
2. 组长可创建账号、导入值班表并看到校验结果。
3. 开发人员提交完整表单后获得唯一编号和自动负责人。
4. 所有已确认的时间、阈值、不可参与和公平排序规则都有自动化测试。
5. 运维管理员可查看全量任务，只能叫号、完成或转交自己的任务。
6. 叫号后开发人员立即看到执行中状态，并产生 `TASK_CALLED` 事件。
7. 组长可调整任务、批量重新分配并查看完整历史。
8. 已完成实际耗时正确计入操作开始日期所在月份的最终负责人。
9. 并发取号不会产生重复编号或错误的任务数量判断。
10. 所有关键变更均可在审计日志中追溯。
